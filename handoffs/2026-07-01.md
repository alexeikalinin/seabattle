**Real critical bug found and fixed — `ProceduralAudio`**
- `ControllerUI`'s READY/attack/placement handlers call `audio.playX()` as the *first* statement. In the AirConsole mobile app's embedded WebView, `new AudioContext()` can throw — which silently aborted the whole click handler before it ever sent the action to the screen or gave any visual feedback. This is what made READY (and everything else) look completely dead on real phones.
- Fix: `src/ui/ProceduralAudio.ts` now feature-detects `AudioContext`/`webkitAudioContext` and wraps every `play*()` body in a `safe()` helper that swallows errors — a missing sound effect can never again block a game-critical tap.

**Root cause of "nothing loads on real devices" — wrong AirConsole hash URL format**
- Per commit `a0cef4d` (May): AirConsole's `#<url>` hash must point at the **site root**, not directly at `screen.html`. Giving `#https://host/screen.html` caused AirConsole's own resource resolution to 404 consistently — reproduced identically across ngrok, Cloudflare quick tunnels, and Vercel, so it was never a hosting issue. `index.html` already mirrors `screen.html`'s boot logic for exactly this reason (don't break that invariant).
- Correct format: `https://www.airconsole.com/#https://<your-host>/` (trailing slash, no `screen.html`).

**Real-device test — confirmed working**
- Vercel project `battleship-duel` had Deployment Protection (Vercel Authentication) enabled, which blocked phones from reaching the deploy (302 → SSO redirect, plus `x-frame-options: DENY` breaking AirConsole's iframe embed regardless). User disabled it in Project Settings → Deployment Protection.
- After that + the URL-format fix, two real phones connected successfully via the AirConsole app and code entry.
